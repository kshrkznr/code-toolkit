# Experiment: Project Knowledge as an Explanation-Model Workbench

> Source: conversation pickup, 2026-08-02.

## Starting observation

Project Knowledge was introduced as a place to preserve project know-how and
development observations.

During CTK development, however, relatively few structures began as stable
decisions that could immediately be documented as know-how. Most emerged
incrementally through implementation, observation, and conversation.

Project Knowledge therefore began to collect a different kind of material:

- Why does this structure feel natural?
- What problem was it actually solving?
- Which explanation best describes what happened?
- How far has that explanation been validated?

## Current hypothesis

Project Knowledge is functioning as a workbench for explanation models.

It is not primarily a project diary, and it does not have the authority of a
design document. It provides a place to compare observations, explanation
hypotheses, alternative mental models, and reusable conversation snapshots.

```text
Observation
    ↓
Candidate explanation
    ↓
Repeated conversation and use
    ├── explanation becomes stronger
    ├── boundary becomes clearer
    └── explanation stops being useful
```

The useful result is often not a final conclusion. It may simply be an
explanation that makes the project easier to understand than the previous one.

## Possible movement into Knowledge

Some current Knowledge documents originated in this kind of exploration.

When an explanation survives repeated discussions, continues to improve shared
understanding, and gains a stable responsibility, it may move into a Note,
Design Note, Core, or another curated Knowledge role.

That does not make promotion the required destination of every Project
Knowledge entry. An explanation can remain useful as a record of how the
project learned to describe itself.

## Unexpected return to the original purpose

Project Knowledge may eventually fulfill its original purpose by an indirect
route.

It began as an attempt to collect development know-how. It then became a place
to test explanations. If some explanations mature through repeated reuse, they
naturally become know-how.

The project may therefore reach its original destination without having
followed the path originally imagined.

## What to observe

- Do future entries continue to begin as explanation hypotheses?
- Can readers distinguish an explanation model from accepted project
  responsibility?
- Which kinds of repeated use make an explanation reusable enough to become a
  Note or other Knowledge?
- Does preserving alternative explanations improve later review, or merely add
  navigation cost?

## Boundary

This is a description of Project Knowledge's current behavior, not a new
mandatory responsibility for every document in the directory.
