# scale

## Observation: Concept / Contract / Implementation の3層で考え始めた

Go実装の議論を進める中で、実装を次の3層に分けて考えるようになった。

Concept・Contract・Implementationという大分類は有効だったが、実際に整理を進めるとContract自体が複数の役割に分かれていた。

当観察では3層の大分類の役割にスコープをあてて記述する。

```
Concept
    ↓
Contract
    ↓
Implementation
```

### Concept

ツールが提供したい責務や概念。

例:
- Cookbook
- Recipe
- Build Lifecycle
- Persistence Lifecycle

言語や実装には依存しない。

---

### Contract

Conceptを実現するために守るべき振る舞い。

例:
- freeze が生成する内容
- commit が解釈する入力
- apply が保証する結果

Go版でもBash版でも共通になる部分。

---

### Implementation

各言語での実装。

例:
- Bash
- Go
- 将来Rustなど

Contractを満たす実装方法。

---

### 観測

Go実装を始めるまでは、

「BashをGoへ移植する」

という見方をしていた。

しかし実際には、

- Conceptを確認し
- BashからContractを抽出し
- Goで実装する

という作業になっていた。

つまりGo実装は単なる移植ではなく、
**Contractを発見・言語化する作業**でもあった。

---

### この観点が面白い理由

この3層はCTK固有というより、

**設計レビューの観点そのもの**として使える可能性がある。

レビュー中も自然に、

- これはConceptの話？
- Contractの話？
- 実装だけの話？

と分類するようになった。


=========

議論の縮尺

設計の議論をしていると、会話が噛み合わないことがある。

しかし、その原因は意見の違いではなく、見ている縮尺が違うだけの場合が少なくない。

例えば、

「あなたの家は？」

と聞かれたとする。

いきなり住宅地図を開く人はあまりいない。

まずは、

* 世界地図
* 日本地図
* 都道府県
* 市区町村
* 最寄り駅
* 住宅地図

というように、相手と現在地を合わせながら少しずつズームしていく。

逆に、

「この交差点を右です。」

という話をしているときに、日本地図を広げても役には立たない。

必要なのは、目的に合った縮尺である。

⸻

設計の議論も同じである。

例えば、

* プロダクト全体の責務を考える
* Build Lifecycleを考える
* freezeの仕様を考える
* Goの実装を考える

これらは別々の話ではない。

同じ対象を、異なる縮尺で見ているだけである。

必要に応じてズームインし、必要に応じてズームアウトする。

⸻

縮尺という言葉は、抽象度という言葉よりもしっくりくる。

抽象度という表現には、どこか上下関係の印象がある。

「こちらが上位」
「こちらが下位」

というように聞こえやすい。

しかし縮尺には上下はない。

世界地図は住宅地図より偉いわけではない。

住宅地図も世界地図より優れているわけではない。

目的に対して適切な縮尺を選んでいるだけである。

⸻

実際の設計も、境界がはっきり分かれているわけではない。

ConceptからImplementationまで、知識は連続したグラデーションになっている。

しかし、そのすべてを同時に扱う必要はない。

まずは、

* Concept
* Contract
* Implementation

程度の粗い縮尺で全体を見る。

必要になればContractの中をさらに細かく見ていく。

つまり、

実態はグラデーションであり、議論では縮尺を切り替えている。

⸻

振り返ると、この考え方はドキュメント構成にも現れていた。

「どの文書に書くか」を決めているように見えて、実際には

「今どの縮尺で議論するか」

を揃えていたのである。

Coreでは責務を扱う。

Notesでは背景や設計判断を扱う。

Sourceでは実装を扱う。

Knowledge Resolverも同様である。

最初からすべての文書を読むのではなく、現在の議論に適した縮尺の文書から読み始める。

必要になればズームインし、必要になればズームアウトする。

設計対象は変わらない。

変わるのは、それを見る縮尺だけである。

この考え方だけで設計のすべてを説明できるわけではない。
しかし、議論が噛み合わない理由や、ドキュメントの役割分担を考えるときのメンタルモデルとしては、有効な場面が多いと感じている。
