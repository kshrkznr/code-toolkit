# Hypothesis: Knowledge Project as Asynchronous OJT

## Background

Knowledge Project を運用する中で、ドキュメントの役割について改めて考える機会があった。

当初は、

- AI向けドキュメント
- Repositoryの説明
- 設計思想の整理

といった目的を想定していたが、共同設計を通じて別の見方ができるようになった。

現時点では、Knowledge Project は

**OJT (On-the-Job Training) を Repository 上へ写像し、非同期でも追体験できるよう設計したドキュメントアーキテクチャ**

として説明すると、多くの観測結果を矛盾なく説明できる。

これは現時点で最も説明力の高い仮説の一つである。

---

# Observation

共同設計では、

途中からツール自体の説明を行う時間が減り、

自然と

- 「CTKならこちらが自然」
- 「この責務なら Runtime」
- 「Futureで十分」

のようなプロジェクト固有の会話へ移行した。

これは単語を覚えたというより、

プロジェクトの考え方や文化へ参加していく感覚に近かった。

この体験は、

新しいツールを学習するというより、

新しいプロジェクトへ参画し、

OJT を受けながら共通認識を形成していく体験によく似ていた。

---

# Mapping

Knowledge Project の各ドキュメントは、

OJT における役割へ自然に写像できる。

| Knowledge Project | OJTでの役割 |
|------------------|------------|
| README | プロジェクト紹介・初日の案内 |
| Resolver | メンター・次に読むものの案内 |
| Knowledge Core | チーム共通の考え方・基本教育 |
| Analogy | 先輩が使う比喩・理解の補助 |
| Author's Recipe | 「私はこう理解している」という解釈の共有 |
| Experiment | 雑談・経緯・試行錯誤・未整理の発見 |

この写像では、

各ドキュメントは知識を整理するためではなく、

理解が育つ順番を構成する役割を持つ。

---

# Author's Recipe

今回最も役割が明確になったドキュメント。

Author's Recipe は、

ベストプラクティスでも、

設定例でもない。

OJT において先輩へ

「どう考えているんですか？」

と質問したときに返ってくる説明を文章化したものである。

Knowledge Core が一般論を説明するのに対し、

Author's Recipe は作者自身のメンタルモデルを共有する。

そのため、

Core だけでは理解しづらい概念を補完する役割を持つ。

---

# Experiment

Experiment は完成した知識ではない。

設計中の会話や、

迷った経緯、

試した結果など、

通常は雑談として消えてしまう情報を保存する場所である。

これは設計の正解を示すものではなく、

設計が育つ過程を追体験するための材料として位置付けられる。

---

# Resolver

Resolver はドキュメントマップではない。

現在の理解段階に応じて、

「次に何を読むべきか」

「まだ読まなくて良いもの」

を案内する、

OJT におけるメンターの役割に近い。

そのため、

Knowledge Project はドキュメントの集合ではなく、

理解が育つ導線そのものを設計していると考えられる。

---

# AI

当初は AI 向けドキュメントという側面を強く意識していた。

しかしこの仮説では、

Knowledge Project は AI 専用ではなく、

OJT を非同期化した結果として、

AI にも利用しやすい構造になっていると考える。

現代では AI が Repository へ参画する機会が増えているため、

結果として AI が主要な利用者になる可能性は高い。

しかし対象は AI に限定されない。

人間・AI を問わず、

新しくプロジェクトへ参加するメンバー全体を対象として考える方が、

現在の運用結果を自然に説明できる。

---

# Open Questions

この仮説はまだ検証途中であり、

以下は今後も観測を継続したい。

- 他の Repository でも同様の構成は有効か。
- 他の AI でも同じような OJT 体験が再現されるか。
- 人間同士のオンボーディングでも同じ効果が得られるか。
- OJT に写像できない責務は存在するか。

Knowledge Project は、

OJT そのものを再現することが目的ではない。

しかし、

OJT を写像するメンタルモデルとして見ることで、

現在のドキュメント構成や共同設計の体験を、

最も少ない矛盾で説明できるように感じている。

---

RAGが『必要な情報を届ける仕組み』だとすれば、Knowledge Projectは『その情報をどう解釈するかというプロジェクト文化をオンボーディングする仕組み』
