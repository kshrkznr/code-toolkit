# Project Knowledge Notes

Project Knowledge Notes preserve reusable observations about how CTK evolved
and how collaborators have worked with it.

They are loose guidance rather than specifications. A Note may help a later
conversation, review, or design decision without requiring the reader to
reconstruct the full exploration that produced it.

## Responsibility

A Project Knowledge Note is responsible for making a reusable observation
available to future work.

It may record:

- a pattern that appeared repeatedly during development
- a useful way to frame a design or documentation question
- an observed collaboration or review practice
- context that helps explain how a current idea became understandable

When the question, alternatives, or uncertainty are still the important part,
the material belongs in an Experiment instead.

## Navigate by question

Start with the question closest to the current work:

- How did conversation shape CTK's concepts and Knowledge structure?
  → [Knowledge Structure Emerged from Conversation](note.conversational-knowledge-evolution.md)
  and [Conversation-first Concept Development](note.development-style.md)
- How can shared Knowledge or review material support collaboration?
  → [Knowledge as Shared Context](note.knowledge-context.md) and
  [Collaborative Review Surfaces](note.collaborative-review-surfaces.md)
- How did navigation and documentation review practices emerge?
  → [The Resolver Emerged from Repeated Navigation](note.documentation-resolver.md)
  and [Documentation Navigation and Review](note.documentation-review.md)
- How have naming and analogy helped expose or communicate responsibilities?
  → [Naming](note.naming.md), [Analogy as a Bridge](note.analogy.md), and
  [Analogy as a Design Review Tool](note.analogy-design-review.md)
- How has raw material been reviewed without losing uncertainty?
  → [Raw Inventory by Theme and Responsibility](note.raw-inventory.md)
- What did platform-specific failures reveal about integration boundaries?
  → [Platform Differences as Boundary Evidence](note.platform-boundary-evidence.md)

These are entry routes, not a required reading order or an exhaustive catalog.

## Boundary

Project Knowledge Notes do not define:

- accepted CTK responsibilities or Concept APIs
- behavioral or representation Contracts
- mandatory collaboration or documentation methods
- unresolved hypotheses whose exploration is still active

Use [Project Knowledge](../README.md) to choose another knowledge-lifecycle
role. Use [Experiments](../experiment/README.md) when preserving a question,
exploration, rejected path, or candidate direction matters more than presenting
a reusable observation.

## Local guidance

Each Note should make its observation and applicability understandable, but no
shared heading template is required. Add related links when they provide a
natural next step.
